# 曜聖景觀社群內容工作室 MVP 設計規格

## 1. 目標

第一階段建立一套可持續使用的「高品質圖文生成＋人工審核」工具，讓曜聖景觀能以真實工程素材，產出適合 Facebook、Instagram 與 Threads 的品牌內容。

本階段的成功不以「AI 有產出」為準，而以內容是否真實、自然、可直接使用且容易審核為準。系統必須降低 AI 套話、保護案場隱私，並保留每一項工程敘述的事實來源。

## 2. 已確認的營運決策

### 2.1 目標與客群

- 首要目標：建立專業信任，穩定支持未來的 LINE／電話詢價。
- 客群優先順序與內容占比：
  1. 建商 `50%`
  2. 公司開發空間 `30%`
  3. 個人透天豪宅 `20%`
- 比例以最近 20 篇內容的滾動視窗計算，不要求每一週精準切割。

內容必須優先呈現企業決策者在意的工程可靠度，包括協作、進度、動線、排水、耐用性、後續養護與整體品質；個人住宅內容則可增加生活感、隱私、水聲、視線與客製細節。

### 2.2 圖片原則與視覺比例

- 只以曜聖的真實工程照片為主體。
- AI 可協助挑圖、分類、品質評分、裁切建議與版型選擇，但不得生成虛構案場，也不得增刪植栽、石材、水景或施工成果。
- 可進行的自然修整包括：曝光、白平衡、對比、有限度透視校正、裁切、格式轉換、尺寸輸出、EXIF 移除，以及經人工確認的人臉／車牌／門牌模糊。
- 視覺類型比例：
  - A 真實作品主導 `30%`
  - B 景觀藝誌 `60%`
  - C 專業知識圖卡 `10%`
- 比例以最近 20 篇含圖片內容的滾動視窗計算。

### 2.3 發文頻率對應的備稿量

系統同時支援單次手動生成與每週自動備稿。自動備稿只建立待審核草稿，不會對外發布。

- 週一、三、五：各建立一組 FB／IG／Threads 跨平台內容包。
- 週二、四、六、日：各建立一篇 Threads 專屬草稿。
- 每週合計：3 篇 FB、3 篇 IG、7 篇 Threads 草稿。
- 當可公開素材不足、案場事實不完整，或會違反客群／視覺冷卻規則時，系統寧可少產，不以重複或虛構內容補足數量。

### 2.4 審核模式

- 第一階段只有一位管理者。
- 所有生成內容都必須人工核准。
- 核准後只提供下載與複製，不串接社群平台發布。
- 每週備稿完成後可發送 LINE 通知，通知只包含摘要與安全的審核頁連結。

## 3. 第一階段範圍

### 3.1 包含

1. 單一管理者登入。
2. 案場資料與素材管理。
3. 素材公開權限與隱私狀態。
4. 手動生成單一內容包。
5. 可開關的每週自動備稿。
6. 真實照片的挑選、自然修整、裁切與品牌版型。
7. FB、IG、Threads 差異化文案。
8. 自動品質、事實、隱私與重複檢查。
9. 三平台並排審核、局部重生、換圖與修改。
10. 核准、退回、版本與操作紀錄。
11. 各平台完稿與 ZIP 素材包輸出。
12. 可選的 LINE 待審通知。

### 3.2 不包含

- Meta Business 帳號設定。
- Facebook、Instagram、Threads API 串接。
- 社群排程與自動發布。
- 發布失敗重試。
- 按讚、留言、觸及或詢價成效回收。
- AI 生成或改造案場景觀。
- 影片上傳、剪輯、Reels 或其他影片輸出。
- 多使用者、多公司或外部合作方權限。

## 4. 核心流程

### 4.1 素材進站

管理者建立案場並上傳 JPG、PNG、WebP 或 HEIC 圖片。系統建立縮圖、移除公開輸出中的 EXIF，並分析重複、清晰度、曝光與可能的敏感資訊。影片素材留待後續階段處理，不在本 MVP 的上傳與輸出範圍內。

每項素材必須標記以下其中一個狀態：

- `可公開`
- `需模糊或裁切後公開`
- `不可公開`
- `尚未確認`

只有 `可公開`，以及已完成必要處理的 `需模糊或裁切後公開` 素材可進入生成流程。

### 4.2 案場事實卡

每個案場使用結構化事實卡，至少包含：

- 對外可用案名與地區層級。
- 客群與場域類型。
- 客戶需求或現場問題。
- 實際服務項目。
- 已確認的工法、材料、植栽或設備。
- 現場限制與曜聖的處理方式。
- 可證明的完成結果。
- 可用 CTA 與聯絡方式。
- 禁止公開的資訊。

系統不得從照片自行推定植物品種、材料規格、客戶身分、工程效果或客戶評語。欄位不足時，內容包改為 `需補資料`，不得用合理猜測補齊。

### 4.3 內容生成

一次生成工作先鎖定事實卡版本，再依下列順序處理：

1. 選定客群、內容角度與視覺類型。
2. 按清晰度、構圖、重複度、隱私風險與近期使用紀錄挑選圖片。
3. 產生圖片構圖、裁切與版型候選。
4. 從同一份內容核心產生三平台版本。
5. 執行事實、語氣、隱私、重複與格式檢查。
6. 通過檢查後建立不可變的待審版本。

每週自動備稿遵守最近使用冷卻期，避免短期內重複同一主圖、同一標題句型、同一 CTA 或同一內容角度。

## 5. 文案設計

### 5.1 品牌語氣

- 台灣繁體中文，自然、克制、具體。
- 像熟悉現場的景觀專業者分享判斷，不像廣告代理商堆疊形容詞。
- 一篇只說清楚一個主要觀點。
- 優先使用可觀察的細節：視線、日照、排水、水聲、動線、樹勢、修剪原因、維護方式與施工協作。
- 可以有情緒與生活感，但不能替客戶虛構感受或評語。

### 5.2 平台差異

- Facebook：完整案例脈絡，說明需求、現場判斷、作法與結果，可加入溫和詢價引導。
- Instagram：文字較精簡，配合圖片順序，聚焦畫面、設計細節與一句可記憶的主題。
- Threads：像現場筆記或專業觀察，一篇一個觀點，減少硬性 CTA，不複製 FB 長文。

### 5.3 去 AI 味規則

系統必須檢查並降低下列模式：

- 「不只是……更是……」等固定對仗句型。
- 「匠心打造」、「療癒秘境」、「完美融合」、「注入靈魂」等空泛詞。
- 三段以上結構完全相同的排比。
- 過度使用問句、驚嘆號、Emoji 與 Hashtag。
- 缺乏案場事實支撐的形容詞。
- 每篇都用相同開場、CTA 或結尾。

每一項工程敘述都要保存所引用的事實卡欄位。審核者可查看「這句話根據什麼生成」。

## 6. 圖片處理與輸出

### 6.1 圖片處理

- 使用現有的 `heic-convert` 與 `sharp` 能力處理 HEIC、縮圖、裁切、色調與輸出。
- 原始素材保留不覆寫；所有處理結果另存新版本。
- 系統可提示可能的人臉、車牌、門牌或文件，但不確定時必須交由人工確認。
- 品牌文字與 Logo 由固定模板渲染，避免生成式圖片模型產生錯字或扭曲識別。

### 6.2 輸出內容

核准的內容包至少包含：

- 各平台使用的圖片檔。
- FB、IG、Threads 貼文文字。
- 圖片替代文字。
- 建議的圖片順序。
- 建議發布日與內容客群標籤；僅供人工參考。
- 案場、事實卡版本、草稿版本與核准時間。
- 可單檔下載，也可下載一個 ZIP 素材包。

## 7. 審核工作台

審核頁採三區設計：

1. 左側：待審核、需補資料、已核准、已退回，以及案場素材庫。
2. 中央：FB／IG／Threads 切換、圖片與文案預覽。
3. 右側：品質檢查、事實來源、核准與退回操作。

管理者可以：

- 直接編輯文字。
- 只重生選取的段落，不覆蓋人工修改的其他內容。
- 更換圖片或調整裁切。
- 單獨退回某一平台版本。
- 整包核准三平台內容。
- 查看所有版本與修改來源。

每次人工編輯、局部重生、圖片更換、退回、核准與匯出都建立稽核紀錄。已核准版本不得被背景工作覆寫；後續修改必須建立新版本並重新核准。

## 8. 狀態與資料模型

### 8.1 主要狀態

內容包狀態為：

`需補資料 → 可生成 → 排隊中 → 生成中 → 品質檢查 → 待審核 → 退回修改 → 已核准 → 已匯出`

錯誤不會假裝成完成狀態；失敗工作保留於 `生成失敗`，可查看原因並重新執行。

### 8.2 主要資料實體

- `projects`：案場基本資料與客群。
- `project_fact_versions`：不可變的案場事實卡版本。
- `assets`：原始素材、公開權限、品質與隱私狀態。
- `content_briefs`：客群、角度、平台、視覺類型與 CTA。
- `generation_jobs`：手動或每週工作、嘗試次數、狀態與錯誤。
- `content_packages`：同一主題的跨平台內容包。
- `platform_variants`：FB、IG、Threads 的文案與媒體配置。
- `draft_versions`：每次 AI 或人工修改的版本。
- `reviews`：核准、退回、理由、時間與操作者。
- `exports`：核准素材包與下載資訊。
- `brand_rules`：品牌詞彙、禁用語、CTA 與已確認的優良範例。

## 9. 技術架構

### 9.1 操作層

- 沿用現有 React／Vite 專案。
- 新增受保護的內容工作室路由與元件。
- 公開品牌網站和內容工作室共用品牌 Token，但內容工作室不出現在公開導覽。

### 9.2 資料層

- Supabase Auth：單一管理者 Email 登入。
- Supabase Postgres：案場、工作、草稿、版本與審核資料。
- Supabase Storage：原圖、預覽、處理版本與核准完稿。
- 存取政策只允許已登入管理者讀寫；公開網站不得直接列出原始素材容器。

### 9.3 自動化層

- n8n 接收手動生成請求並執行每週自動備稿。
- 背景工作負責圖片處理、AI 內容流程、品質檢查與 LINE 通知。
- 所有工作具有唯一鍵與可重入設計，避免重試或排程重疊造成重複草稿。

### 9.4 AI 與確定性處理的邊界

- AI：圖片內容標記、候選排序建議、內容角度、事實約束寫作、平台改寫與語氣檢查。
- 確定性程式：檔案轉換、尺寸、裁切座標、Logo、文字渲染、版本、狀態轉換、權限與 ZIP 匯出。
- AI 輸出永遠不能直接改寫已核准內容或公開權限。

## 10. 錯誤與安全處理

- 事實不足：改為 `需補資料`，停止生成。
- 未確認公開權限：素材不得進入草稿。
- 損壞或不支援的檔案：隔離單一檔案，其餘素材繼續；案場保留警告。
- 隱私辨識不確定：強制人工確認，未確認前不得核准。
- AI、儲存或工作流暫時失敗：最多自動重試三次，採遞增等待時間。
- 三次仍失敗：保留錯誤、輸入版本與已完成步驟，不產生半套完稿。
- 排程或按鈕重複觸發：相同唯一鍵只允許一個有效工作。
- LINE 通知失敗：不影響草稿狀態；後台顯示通知失敗，可手動重送。
- 原始素材不覆寫；刪除、權限變更與人工隱私豁免都必須留存稽核紀錄。

## 11. 測試策略

### 11.1 單元測試

- 案場事實卡完整性。
- 客群與視覺比例的滾動配額。
- 禁用語、重複句型、CTA 與字數規則。
- HEIC／JPG／PNG／WebP 轉檔、尺寸與 EXIF 移除。
- 狀態轉換、版本建立與核准後不可覆寫。
- 唯一工作鍵與重試次數。

### 11.2 整合測試

- 上傳素材後建立縮圖與分析結果。
- 從事實卡產生三平台版本並保存來源對應。
- 圖片模板渲染與 ZIP 匯出。
- n8n 手動觸發、每週觸發、失敗重試與去重。
- LINE 通知不影響內容工作本身。

### 11.3 端到端測試

完整驗證：登入 → 建立案場 → 上傳素材 → 設定公開權限 → 完成事實卡 → 生成 → 編輯／局部重生 → 退回或核准 → 下載素材包。

測試至少覆蓋一個建商、一個企業開發空間及一個個人豪宅案例，以及手機和桌機審核流程。

## 12. 驗收標準

1. 100% 工程敘述可追溯到明確的案場事實卡欄位與版本。
2. 0 筆未授權或未完成隱私確認的素材可進入核准完稿。
3. 所有核准圖片尺寸、裁切、Logo 與文字均可直接使用，不需外部設計軟體補救。
4. 使用代表三類客群與三種視覺類型的案例，試產至少 20 組內容包。
5. 校準後至少 80% 草稿只需小幅修改即可核准；小幅修改定義為不改變核心角度，且單一平台文案修改不超過原稿 20%。
6. 完整流程可從建立案場一路完成到核准並下載素材包。
7. 生成失敗、重複觸發與通知失敗不會建立重複或半完成的核准內容。
8. 自動化測試涵蓋圖片、文案規則、權限、版本、重試與完整審核流程。

## 13. 後續階段

只有第一階段內容品質與審核流程通過驗收後，才規劃第二階段：Meta 商業帳號設定、官方 API 串接、排程發布、發布重試、成效回收，以及前 30 天人工核准後可切換全自動的治理機制。
